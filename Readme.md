[![CI (main)](https://github.com/V1aDD05/emergency-triage-backend/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/V1aDD05/emergency-triage-backend/actions/workflows/ci.yml)

Backend-сервис для распределения пострадавших по операционным

**⚠️ Предупреждение**
>Проект создан исключительно в образовательных целях и для демонстрации навыков разработки на `C++` (**backend**).
>Алгоритмы медицинской сортировки (триажа) и медицинская логика являются упрощёнными и **не предназначены для реального использования в медицинской практике**, принятия клинических решений или диагностики.
>Для реального здравоохранения требуются сертифицированные системы, прошедшие клинические испытания.

## Концепция и составляющие сервиса
Сервис для оптимизации распределения пострадавших по операционным в больнице. Основной фокус на backend логике

### Обобщённая схема сервиса
```mermaid
flowchart TD
    subgraph Клиенты
        A[Скорая помощь]
        B[Медицинский пост хирургического отделения]
    end

    subgraph Сервер
        C[HTTP API]
        D["Backend-логика\n(приоритезация, очереди)"]
        E[База данных]
    end

    A -- "Отправка данных пациента" --> C
    B -- "Управление операционными, запрос статистики\n \n \n" --> C
    C --> D
    D --> E
    E --> D
    D --> C
    C -- "Ответ (время ожидания, статус)" --> A
    C -- "Данные об операционных и статистика" --> B

```

### Концепция сервиса в целом
**1. Клиент "карета скорой помощи"**
Формирует JSON файл с данными о пациенте (характер повреждений, пол, возраст, и т.д.), отправляет запрос на HTTP API.
*Возможные улучшения: сбор и передача контактных данных пострадавшего, сведений о травмах и хронических заболеваниях.*

**2. Клиент "медицинский пост хирургического отделения"**
Отображает информацию о статусе операционных (заняты или свободны), оценочное время до окончания операции.
*Возможные улучшения: возможность получить статистику операционных бригад (смертность, и т.п.)*

**3. Backend сервер (бизнес-логика)**
Реализует вычисление приоритета помощи пострадавшему. Распределяет пострадавших по операционным на основе приоритета.  Оценивает время ожидания пациентом операции.
*Возможные улучшения: При наличии различных типов операционных, определяет тип требуемой операционной. Определяет статистику бригады*

**4. HTTP API**
Обрабатывает запросы от клиентов "карета скорой помощи" и "медицинский пост хирургического отделения";

**5. База данных**
Хранит приоритизированную очередь пациентов, статус операционных.
*Возможные улучшения: хранение статистических данных*

### Реализуемая составляющая сервиса
- HTTP API;
- Backend сервер;
- База данных;
- Простейшие клиенты.

## Этапы реализации сервиса

**1. "Скелет" In-memory сервера**
- Настройка CMake, CI (GitHub Actions), линтеров.
- Создание заглушек для ключевых компонентов (хранилище, роутер, сервис).
- Документация (модели данных, архитектура).
- Базовые unit-тесты и smoke-тесты для проверки сборки.

Статус: *реализуется*

**2. Сервисный слой и вычисление приоритета**
- Реализация интерфейсов: `IPatientStorage` (in-memory), `PatientService`.
- Внедрение алгоритма расчёта приоритета в соответствии с методикой триажа `SORT`.
- Написание unit-тестов для сервисного слоя и расчёта приоритета.
- Создание простейших HTTP-клиентов (bash/Python) для ручного тестирования.
- Интеграционные тесты API.

Статус: *запланирован*

**3. Управление очередью в операционные (MVP)**
- Реализация класса `TriageQueue` для управления очередями.
- Алгоритм распределения пациентов по операционным на основе приоритета.
- Пересчёт очереди при изменении статуса пациента или операционной.
- Оценка времени ожидания (estimated wait time).
- Интеграционные тесты для проверки логики очереди.

Статус: *запланирован*

**4. Интеграция с базой данных (SQLite)**
- Создание `SqlitePatientStorage`, наследующего `IPatientStorage`.
- Написание миграций (создание схемы).
- Переключение между in-memory и SQLite через конфигурацию.
- Тесты на сохранность данных и производительность.

Статус: *запланирован*

**5. Реализация многопоточности**
- Переход на многопоточную обработку запросов (пул потоков, async).
- Защита общих данных (мьютексы, шардирование).
- Нагрузочное тестирование (например, с помощью wrk или ab).

Статус: *запланирован*

**6. Применение Docker**
- Сборка многостадийного Docker-образа с сервисом.
- Настройка переменных окружения (порт, путь к БД и т.д.).
- Добавление health-check и мониторинга (логирование в stdout).
- Документация по запуску в контейнере.

Статус: *запланирован*

**7. Обработка статистики**
- Сбор и хранение статистических данных (смертность, загрузка ОР, время ожидания).
- Эндпоинты для получения статистики.
- Визуализация (если захочешь) или просто JSON-ответы.

Статус: *запланирован*

## Пространство имён
Все компоненты проекта находятся в пространстве имён `emergency`. Заголовочные файлы расположены в `include/emergency_triage/`, что соответствует этому пространству имён.

**Пример использования**

```cpp
#include "emergency_triage/storage/data_structures.hpp"

uint8_t age = 10;
emergency_triage::DemographicData demographicData(age);
uint8_t newAge = 12;
demographicData.setAge(newAge);

```

## Ветки
Следуем [Git Flow](https://nvie.com/posts/a-successful-git-branching-model/) с дополнениями:
- `main` - стабильная ветка для релизов (в пет-проекте сюда попадают результаты крупных этапов через release/*).
- `dev` - основная ветка разработки;
- `stage/*` - для крупных этапов (например, `stage/1`, `stage/2`). Создаются от `dev`, после завершения сливаются обратно в `dev`.
- `bugfix/*` - для исправления ошибок.
- `release/*` - подготовка релиза. Создаются от `dev`, сливаются в `main` и `dev`.
- `hotfix/*` - для срочных исправлений. Сливаются в `main` и `dev`.

## Стиль коммитов
Начиная с `v0.1.0` коммиты следуют [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), конфигурацию [@commitlint/config-conventional](https://www.npmjs.com/package/@commitlint/config-conventional). Ниже приведена таблица применяемых типов:

| Тип | Характер изменения | Описание |
|-----|--------------------|----------|
| **feat** | Новая функциональность | Добавление новой функции или возможности |
| **fix** | Исправление ошибки | Исправление бага в коде |
| **docs** | Документация | Изменения, касающиеся только документации (в том числе - комментарии в коде) |
| **refactor** | Рефакторинг | Изменение кода, которое не исправляет ошибку и не добавляет новую функцию (например, переименование переменной, вынос функции) |
| **perf** | Производительность | Изменения, направленные на улучшение производительности (например, оптимизация алгоритма, реструктуризация данных) |
| **test** | Тесты | Добавление новых или исправление существующих тестов |
| **build** | Система сборки | Изменения, затрагивающие систему сборки или внешние зависимости (например, обновление `CMakeLists.txt` или версии библиотеки) |
| **ci** | Непрерывная интеграция (CI) | Изменения в конфигурации CI (например, обновление `.github/workflows/ci.yml`) |
| **chore** | Обслуживание | Другие тривиальные изменения, не затрагивающие исходный код или тесты (например, обновление `.gitignore`) |
| **style** | Стиль кода | Изменения, не влияющие на смысл кода (форматирование, пробелы, и т.д.) |
| **revert** | Откат изменений | Отмена одного из предыдущих коммитов |

## Сборка
Проект разрабатывался и тестировался на **Ubuntu 22.04**. Для других операционных систем проверок не производилось, но сборка, скорее всего, возможна при установке аналогичных зависимостей.

### Установка зависимостей в Ubuntu/Debian
#### Обязательные (требуются для сборки)
- build-essential;
- cmake (≥ v. 3.15);
- git;
- libsqlite3-dev;

Для установки выполните команды, указанные ниже.

```bash
sudo apt update
sudo apt install -y build-essential cmake git libsqlite3-dev
```

#### Дополнительные инструменты (для разработчиков)
- clang-format (≥ v. 15.0) - для форматирования кода;
- jq - для обработки JSON в скриптах;
- curl - для HTTP-запросов (например, в smoke-тестах).

```bash
sudo apt install -y clang-format jq curl
```

### Запуск сборки
Запустите скрипт, выполняющий конфигурацию CMake, сборку проекта и запуск тестов.

```bash
./build.sh
```
